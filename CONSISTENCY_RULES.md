# Consistency Rules — Cross-Protocol, Must Never Drift

This is the single canonical copy of the cross-protocol rules — `MASTER_SYSTEM_SPEC.md` §5 is a short pointer back to this file, not a second copy (that duplication used to drift out of sync with itself; see this file's own rule 15 for a concrete example of the kind of drift that caused). There is no automated per-message API/CLI call in the current architecture — Claude Code itself reads this file fresh from disk, alongside whichever single protocol file (`SCREENER_v3.md` / `MONITOR_v2.md` / `STRATEGY_v3.md`) is active, and applies the rules directly. If a rule needs to change, it changes here, once — never patched around in code, never duplicated into a second file.

These are the rules that were tightened during real use. If the bot (or a future re-implementation of the protocols) ever regresses on these, it reproduces mistakes already caught and fixed once:

1. **No invented price levels.** Every stop, target, or SR level must cite its source: chart label, CSV OHLC, or an explicitly shown calculation (Fibonacci extension, measured move). A level with no source is not shown.
2. **"Base" for a stop = the structure the specific thesis actually depends on** — not the nearest-looking SR line from an unrelated part of the chart. Test: "does price have to pass through this level to reach the trigger?" If no, it's not the base.
3. **Target validity requires two independent checks, both must pass — checked ONCE, at entry (trigger price), never re-graded against a moving current price:** (a) ≥1.5x ATR14 from the entry/trigger price, (b) R:R ≥ 2:1 at entry (2.5:1 if the target sits in the 1.0x–1.5x ATR band). A level failing either at entry is a **Checkpoint**, not a sellable target. Once a target passes at entry it stays a valid target for the life of the position — R:R and ATR-distance mechanically shrink as price runs toward any target (less reward left, same or smaller risk); that shrinkage is normal stock behavior, not evidence the target went bad, and must never re-label an already-qualified target as a Checkpoint. Instead, when an open position's current price closes within 0.5x ATR14 of a stored target, that is a **take-profit heads-up** (a plain "you're close, decide: trim or hold" flag) — not a validity re-test. (Changed 2026-07-31: the previous "current price for open-position management" wording made every winning trade's target fail its own gate on approach, purely because reward shrinks faster than risk near a target — a real LLY/GOOGL incident where correct math produced a nonsense conclusion.)
4. **Stop-noise floor: ≥0.7x ATR14** between reference price and stop, in both directions — entry (SCREENER_v3) and any stop update on an open position (STRATEGY_v3). A stop inside this band is statistically noise, not signal.
5. **Micro before macro, two directions not two depths.** When two setups are shown, they should be the two nearest-in-time plausible scenarios (e.g. "holds and continues" vs. "pulls back first") — not two versions of the same direction at different depths, and not a "preferred vs. backup" sequence. Both can be tracked in parallel until one triggers. **Not optional — every report (SCREENER_v3, and MONITOR_v2 for an existing thesis) must show at least 2 setups (Primary + Alternate), every time, including Watchlist and No Trade outcomes** — never just Primary alone. If the second scenario has no cited level yet (e.g. a deeper capitulation zone that hasn't formed), state that explicitly rather than omitting the Alternate row entirely — an honest "not yet defined" still satisfies this rule; a missing second setup does not. This applies in the widget/PNG exactly as much as the full report — a widget showing only one setup card is an incomplete render, not an acceptable summary. (Found via a real miss: three fresh screener runs — MU, ONDS, ANET — were all sent with only a single setup shown, and no visible "movement potential" field at all in the widget, even though rule 17 already required it; both gaps were only caught because the user asked why, not by anything in this file forcing it strongly enough. Rule 5 always technically implied 2 setups, but "when two setups are shown" read as descriptive, not mandatory — rewritten above to close that reading.)
6. **No target above all-time-high / no data above current range → Runner-only.** Trailing stop, no R:R displayed. **Size is unchanged — a full risk unit, like every other trade (owner's decision, 2026-08-10).** This clause used to read "reduced size", which directly contradicted rule 28: rule 28 removed every size multiplier on 2026-08-03 and states that with no derates left the only correct answer is one full risk unit. Two rules giving two different sizes for the same trade is exactly the drift this file exists to stop, so the owner settled it in favour of rule 28. Runner-only changes how the position is MANAGED (everything trails, nothing is sold at a fixed price); it no longer changes how big it is. This applies equally to fresh entries (SCREENER_v3) and existing positions that have simply run out of chart (STRATEGY_v3). **This rule is easy to misapply to a different, more common case — read carefully:** rule 6 fires only when NO number above the reference price passes rule 3's gates at all — there is genuinely nothing to cite. It does NOT fire just because the ceiling of available data (the all-time-high itself, or the edge of the fetched history) happens to be the qualifying target. If the all-time-high (or highest fetched bar) itself passes rule 3 (≥1.5x ATR AND R:R≥2:1), that is a normal single qualifying target under rule 7 — 40% there / 60% Runner, R:R shown, exactly like any other target — the only thing rule 6 contributes in that case is that the 60% Runner tranche has nothing further to trail toward except a trailing stop, since there's no data past it. Do not skip the target/allocation table, and do not withhold the R:R figure, just because the qualifying target happens to sit at the edge of known data. (Found via a real miss: an all-time-high target that passed both gates cleanly was presented inline as a plain "supported target" but the mandatory 40%/60%-Runner allocation table was omitted entirely, on the mistaken assumption that "no data above" meant "skip the table" rather than "this changes what the Runner tranche does, nothing else.")

**The Runner's trailing stop is not exempt from rule 4's noise floor — "below the daily low" is not a complete instruction on its own.** When rule 6 fires and there's no qualifying target, the trailing stop must be selected the same way STRATEGY_v3.md's post-tranche stop-placement method already specifies: the highest daily low that still clears ≥0.7x ATR14 from the current price — not simply the most recent daily low. If the most recent low is too close (inside the noise band), go to the next real low further back, exactly like the post-tranche method already requires; do not use a closer level just because it's the latest bar. A bare "trailing stop below the daily low" with no ATR check is under-specified and reads as if any daily low qualifies. (Found via a real gap, not yet an actual miss: the Runner-only wording in SCREENER_v3.md/STRATEGY_v3.md never cross-referenced the noise-floor test at the point of use, even though rule 4 technically already covers "any stop update on an open position" — the same "stated once elsewhere, missed at the point of use" pattern behind several other rules on this list.)
7. **Exit allocation standard:** single qualifying target → 40% there / 60% Runner. Two qualifying targets → 40% / 35% / 25% Runner. Never split around a Checkpoint. **Every setup shown gets this analysis independently — Alternate is not exempt just because it's second or still pending.** Each setup has its own hypothetical entry/stop (rule 14), so it must get its own target scan (rule 11's wall check, rule 3's gates, rule 12's alternates) computed from *that setup's own* entry/stop — never left as trigger/stop only while only Primary gets a target table. Two different setups often reach the same nearby resistance with very different quality: a deeper Alternate entry (lower price) frequently produces a *better* R:R to the identical target than Primary's entry, which is worth surfacing, not hiding by skipping the analysis. The only valid exception is when the Alternate genuinely has no level to anchor a hypothetical entry from yet (no real support/resistance identified) — state that plainly rather than inventing one, same standard as rule 1. (Found via a real miss: three fresh screener runs — MU, ONDS, ANET — each had their Primary setup's target fully analyzed but their Alternate left as trigger/stop only, with no target scan attempted at all. Re-run properly: ANET's Alternate, entering lower via a reclaim at ~162 instead of chasing the 179.80 breakout, turns the same 179.80 level into an actual qualifying target — R:R 2.54:1, distance 1.82x ATR — where Primary's own entry left it as just the trigger itself with nothing beyond it in range. MU's Alternate similarly improves R:R to the same 1089.29 level from 1.78:1 (Primary, fails) to 8.19:1 (Alternate's deeper entry, passes easily) — the entry price the setup uses changes whether the identical target even qualifies.)
8. **Core/Layer1 holdings are exempt from 1–7.** A position explicitly flagged as a passive structural holding (e.g. SPY/QQQ inside a fixed portfolio allocation) gets a wide structural stop only, no numeric target, no 2H alerts, no tranche table. This exemption must be explicit per position, never inferred from size or age.
9. **2H confirmation ≠ daily confirmation, and its meaning depends on context:** for a *new* entry not yet open, a 2H close beyond the trigger is a "Starter allowed, present both options" situation (MONITOR_v2). For an *existing* open position, a 2H break of a key level is a re-check trigger, not a reason to add (STRATEGY_v3). These are two different rules that happen to both mention "2H" — never conflate them.
10. **Cooldown after a stop applies only to real exposure.** A thesis invalidated before any entry (MONITOR_v2, 🔴 with zero fills) can be re-evaluated same-day if structure changes. A position actually opened and stopped out follows the no-re-entry-same-day rule.

11. **Resistance-wall scan required before testing any single target (prerequisite to rule 3).** Before running rule 3's ATR/R:R check on any target, first locate every local high between the current price and the furthest target being tested — not just the two or three most visually obvious peaks ("visually obvious" is a bias: easy to spot a tall or fresh high, easy to miss intermediate highs of similar size nearby). Chain neighbor-to-neighbor in ascending price order — each high tested against the high next to it in the sorted list, NOT against one fixed anchor point (e.g. the lowest high in the range). If the neighbor-to-neighbor gap is ≤~3% (or ~0.5x ATR14, whichever is larger), the two highs belong to the same wall; keep chaining upward as long as the next gap stays within tolerance. **The wall ends only when one gap exceeds the tolerance** — not at a fixed count or a fixed price range from the first anchor (a fixed anchor can cut a real wall in half if highs far from the anchor but close to each other fall outside a fixed range). 3 or more highs chained this way = a **resistance wall** — label it explicitly before testing any individual level inside it. The breakout trigger for an identified wall is a close above the wall's highest point (the top of the chain), not its lowest/first level. Testing only the most salient peaks and silently skipping the rest is not a complete scan, even if the levels tested happen to fail correctly. Fewer than 3 chained highs: not a wall, evaluate levels individually as usual. (Found via a real gap: a case with 7 distinct daily highs packed into an 8-day window was only partially scanned — 2 of 7 levels tested — and never labeled a wall, even though a separate case with looser clustering, 5 peaks over ~3 months, was correctly identified and named. This rule's first version used a fixed anchor point and was refined to chained neighbor-to-neighbor testing for the reason noted above.)

**Recursive step, required once a level passes rule 3's gate — do not stop at the first qualifying level:** Once a level passes rule 3's ATR/R:R gate, before treating it as the final target, re-run this same chaining check starting from that level — check whether it is itself part of a *second* 3+-touch chained wall further up. If it is, the real qualifying target is the top of that second wall, not the level first found. Repeat until reaching a level that is not part of any further chain, or until the fetched history runs out (then Runner-only per rule 6). (Found via a real miss, the PLTR review: 157.78 initially looked like a valid, gate-passing target, but 157.78–163.70 turned out to be its own separate 3-touch chained wall — the actual correct single target was 163.70, the top of that second wall, not 157.78. A single pass of the chaining check is not enough when the qualifying level itself sits inside another wall.)
12. **Target-source scan must actively check all 5 authorized methods, not default to raw swing high/low.** If the nearest swing high/low fails rule 3's ATR/R:R gate, explicitly check whether Volume Profile/Anchored VWAP, a Fibonacci extension, a Measured Move, or a defined pattern target passes before concluding "Runner-only/No Trade" — these are not optional fallbacks, skipping straight to "no target" without checking them is itself a miss. A Fibonacci extension's A→B→C anchor must be the specific move the current thesis depends on (same test as rule 2's stop-base rule — not an arbitrary older move that merely looks clean on the chart). An Anchored VWAP must anchor to the event the thesis depends on (gap day, flush day, breakout day) — not a generic long-range VWAP unless the thesis itself spans that range. Anchor selection is contextual judgment and stays with the model; the arithmetic once an anchor is chosen is pure formula and may run in `indicators_core.py`.
13. **Target-source list is closed — a simple moving average (SMA20/50/150) is never an authorized target itself**, even when a real level happens to sit near it. SMA is a trend-detection tool, not a structural price level, and is not on rule 1's source list. If an SMA level coincides with a real target from the authorized list, note the overlap in the technical analysis, but the displayed target must cite the authorized source, not the SMA. A 6th authorized method requires an explicit decision, never silent expansion.
14. **A required section is never silently omitted just because nothing currently qualifies — the protocol's own "pending" mechanism is used instead, never a skipped table.** SCREENER_v3.md's two-setup table has an explicit path for a setup whose trigger candle hasn't formed yet ("no order ready; trigger determined after the confirmation candle forms") — that path gets used, not a decision to present zero setups because "no setup exists yet." The same principle holds for MONITOR_v2 (both setups from the existing thesis stay reported in parallel until one triggers — never silently dropping one because it currently looks unpromising) and STRATEGY_v3 (every open position gets a management-table entry with an action, including explicit "No Action" — never an omitted row). This is a structural-completeness failure, not a numeric one — checked by re-reading the response's own required-section list, not a numeric threshold — precisely because there's no number to check in the first place, the bug is an entire section missing, not a wrong value in a section that exists. (Found via a real miss: a live analysis correctly concluded no setup currently triggers, then incorrectly presented zero setups instead of the required pending-setup structure.)

**This applies just as much to rule 7's targets/allocation table as it does to the two-setup table itself — they are two separate required sections, and "the setup is Pending" is not a reason to skip either one.** If a setup (even a not-yet-triggered one) has a target that passes rule 3's gates, the 40%/60% (or 40/35/25) allocation table is shown hypothetically, exactly the same way the setup's own trigger/stop get shown as "no order ready yet" rather than omitted — a reader should be able to see the full plan before it triggers, not only after. A second, related trap: rubric criterion 1 (R:R≥2.3) failing is a stricter bar than rule 3's basic entry gate (R:R≥2:1 AND ≥1.5x ATR) — a target can fail the rubric's 2.3:1 point *and* still be a fully legitimate, sourced, gate-passing target. State both facts explicitly when this happens (a "0" on the rubric line is not the same claim as "this target is invalid") so a reader skimming the rubric doesn't misread a scoring gap as a disqualification. (Found via a real miss: an all-time-high target that clearly passed the entry gate — 2.25x ATR, R:R≈2.34:1 (this predates the rubric threshold's move from 2.5 to 2.3; at the time it failed the rubric point) — was written into the setup row as a plain target, then the mandatory allocation table underneath was marked "not relevant, no order ready" instead of showing the hypothetical 40%/60%-Runner split; the rubric's "0" was also left unexplained, readable as if the target didn't qualify at all.)

15. **RS window depends on setup type — trend-following vs. reversal, never one fixed window for both.** Trend-following setups (Breakout, Retest, Pullback within an existing HH/HL) measure RS on a fixed 20-trading-day window, every time, for comparability across runs. Reversal setups (Reclaim, Failed Breakdown, Gap-and-Hold after a sharp decline) additionally require a 5-trading-day window — a fixed 20-day window structurally fails almost every reversal thesis regardless of how strong the actual recovery is, since the stock is still statistically "dragging" the crash the thesis is recovering from. Show both windows for a reversal setup — a reversal widget or report with only one RS number is itself an incomplete render. The rubric's RS criterion uses the 5-day figure for reversal setups specifically, the 20-day figure for trend-following setups. (This is the same rule already correctly written into SCREENER_v3.md's own RS-window section — restated here as the canonical cross-protocol copy because this file's footer had drifted out of sync with it. Found via a real gap: the footer below used to say "fixed 20-trading-day lookback, every time" with no exception, directly contradicting SCREENER_v3.md's own rule and a live, correctly-handled UPS report — the footer was simply wrong, not a stricter override, and has been removed rather than reconciled into a second copy.)
16. **"All-time high" and "no data above this level" are claims that must be earned, not defaulted to.** `tv_data.py`'s `get_daily_history()` typically returns ~2 years of bars, not the 5 years the protocol files ask for — call `describe_history_coverage()` on whatever was actually fetched and cite `date_start`/`date_end` in the report. Never write "all-time high" or "no data above this level" unless there's real reason to believe the fetched window covers the stock's actual full trading history (e.g. the fetched start date predates a known IPO/listing date) — bar count alone never proves this. When that reason isn't there, use the scoped wording instead: *"No qualifying target found within fetched history: [date_start] to [date_end]"* — this is the KRE full-vs-truncated-history lesson: the same ticker can look like it has "no data above" or genuinely have data above, purely depending on how much history happened to get fetched that run, and the report must say which situation it actually is.
17. **Movement potential is a separate, informational figure from the sellable target(s) — never gated by rule 3, never confused with a real order.** In addition to the near-term sellable target(s) tested under rule 3, show the stock's longer-range movement potential: identify the base/consolidation range that existed immediately *before* the current trending move began (its high and low), measure that base's height, and project it forward from the breakout point using the standard Measured Move method (`potential = breakout_level + base_height` — see `indicators_core.py`'s `measured_move_target()`). This answers a genuinely different question ("how far could this move plausibly go, big picture") from the tactical target table ("what price do I actually plan to sell at"), and must never be presented as if it were one — label it explicitly every time it's shown, e.g. *"פוטנציאל תנועה — לא יעד מכירה, לא עובר את מבחני כלל 3."* Anchor selection (which base counts as "the" base this move actually broke out of) is contextual judgment, the same test as rule 2's stop-base rule and rule 12's Fibonacci/VWAP anchor rule — the specific consolidation the current rally came from, not an arbitrary older range that merely looks clean on the chart.

**Compute this for a PENDING/hypothetical setup too — never wait for the trigger to actually confirm first.** The instant a setup has a defined trigger level (even one that hasn't fired yet), that trigger level IS the prospective breakout point — project from it immediately, exactly the same way rule 14 already requires showing a hypothetical entry/stop/target for a not-yet-triggered setup. "No current move to anchor from" is NOT a valid reason to skip this whenever any trigger is defined, pending or confirmed — it only applies in the genuinely rare case where a ticker has no setup at all, not even a pending one (e.g. an Alternate scenario with no support level identified yet). Getting this distinction wrong the first time this rule was used live is exactly why this paragraph exists: three fresh screener runs (MU, ONDS, ANET) each had a perfectly well-defined trigger (a wall top, a reclaim level, a chop-zone ceiling) and Potential was still marked "not applicable" for all three — wrong, because a defined trigger is precisely what this calculation needs. Corrected values, same tickers, same trigger levels already on file: ANET (trigger 179.80, base 154.74–179.80) → potential 204.86. MU (trigger ~945, base 891.66–1019.00) → potential 1072.34 — flagged lower-confidence given how tight/immediate that base is, this system's extreme volatility makes a clean base hard to find, but the number still gets computed and shown, not withheld. ONDS (trigger 8.65, base 7.31–8.65) → potential 9.99.

**Not optional, and not satisfied by the full report alone: this field must appear as its own visibly labeled row in the widget/PNG too, every time** — a widget that only shows targets/stops with no Potential row is an incomplete render, the same standard rule 5 sets for the two-setup requirement. (Added after the user asked how "potential" — where a move could ultimately go — differs from the immediate target; it didn't, because this concept didn't exist yet. Explicitly not the same computation as rule 12's near-term Fibonacci/Measured-Move target, which uses whatever nearby swing anchors the immediate thesis; this uses the larger structure preceding the whole current move.)

18. **Regime hard gate — a technically clean setup is not exempt from a hostile market.** Market regime (`SCREENER_v3.md` §א's six-way classification: Risk On / מגמה עולה בריאה (healthy_uptrend) / תיקון בתוך מגמה עולה (pullback_in_uptrend) / ניטרלי-Choppy (neutral_choppy) / Risk Off (risk_off) / שבירת מבנה (structure_break)) has been computed and stored on every thesis since the beginning, but until this rule it enforced nothing — a well-sourced, gate-passing setup in `risk_off` graded exactly like the identical setup in `healthy_uptrend` and produced the same full-size order spec. That's inconsistent with how rules 1–17 already treat other hard facts about the setup: a level with no source, a stop inside the noise floor, or a mis-scanned wall are blocks on the OUTPUT the reader can't miss, never soft warnings buried in the analysis prose — regime gets the same treatment here, because "the arithmetic is correct" is not the same claim as "now is a good time to buy," and only the second claim is what a live order actually asserts.
  - **`risk_off` or `structure_break` → the decision line may never read "Buy Now" or "Buy Only If Confirmed."** Maximum allowed decision is Watchlist. The full analysis — both setups (rule 5), every target scan (rules 3/11/12), the rubric grade — is still produced and saved as a pending thesis exactly as it otherwise would be; the gate blocks the ORDER, not the thesis, the same split rule 6 already draws between "no qualifying target" (still shows the hypothetical allocation table) and an actually-missing section.
  - **`neutral_choppy` → advice only, no size change (changed 2026-08-03, by explicit user direction).** This used to be a ×0.5 position-size multiplier stacked on the volatility multiplier. It is now a plainly-worded caution note stating what the market looks like, what that usually means, and what the user might consider doing — explicitly labelled as a recommendation, not a rule. The user's own reasoning, recorded verbatim because it is the whole justification: *"the market condition should be a caution sign with a recommendation, not something absolute — since we don't know how it impacts the trades."* Three facts back that up: (1) the multiplier was never occasional — `regime_formula.py` returned `neutral_choppy` on **every single trading day from 2026-07-20 onward**, so a "derate" that fires every day is not a derate, it is just a smaller base risk applied silently; (2) rule 26's own 305-trade backtest found the opposite of the assumed effect — Breakout/Retest averaged **+0.36R in `neutral_choppy`**, its *best* regime, and **−0.12R in `healthy_uptrend`**, its only losing one; (3) combined with the volatility and volume multipliers it produced real sized-at-0.2% positions (rule 28). The regime is still computed, still shown on every report, and still stored on every thesis (`market_regime_at_build`) — precisely so the question "does it actually matter?" can be answered from this account's own closed trades in a few months instead of assumed now. `bot/size_policy.ADVISORY_MULTIPLIER_KEYS` enforces the non-effect mechanically: a `choppy`/`regime`/`market` entry may still be passed in a sizing block and is displayed, but is never multiplied in. `regime_formula.describe_regime_he()` produces the note, appended deterministically by `deliver_report.py`.
  - **The hard block stays a hard block.** `risk_off` and `structure_break` still cap the decision line at Watchlist — that half of this rule is unchanged and is stated in the note as a rule, not a recommendation. Only the middle ground (`neutral_choppy`) became advice.
  - **The gate applies twice, not once: at SCREENER_v3 build time, and again at MONITOR_v2's 🟢 trigger confirmation** — re-check the regime fresh at that moment, never reuse the stored `market_regime_at_build` as if it still applies. A thesis built in `healthy_uptrend` that actually triggers while the market has since moved to `risk_off`/`structure_break` gets the same block as if it had been screened today — reported as a prominent warning naming BOTH regimes (built-at vs. now), not silently waved through just because it cleared the gate once at build time. The trigger firing is still reported as an objective fact (the price action happened, same principle as MONITOR_v2's existing "the live trigger/stop deviation never blocks a real 🟢" wording) — what's blocked is the buy order and the `set_status(ticker, 'open_position')` flip; the thesis stays `pending`.
  - **Deterministic backstop, not a second judgment call:** `bot/report_lint.py` cross-checks this rule mechanically after the fact — if a delivered report's own `market_regime` field is `risk_off`/`structure_break` and its own `decision` field is a buy decision, that combination alone is a lint failure, regardless of whether the regime classification itself was the right call. `report_lint.py` never judges the regime — it only checks that Claude's own two output fields don't contradict each other, the identical Category A/Category B split `CLAUDE_CODE_INSTRUCTIONS.md` already draws everywhere else: the regime call stays Category B, "did this report contradict its own regime field" is pure bookkeeping and can safely run in Python. See `SCREENER_v3.md` §א/ב and `MONITOR_v2.md`'s 🟢 tier for the two points of use.

19. **Portfolio risk disclosure — real numbers, never a gate.** Every `/screener` report must state, plainly, in its sizing section: the dollar risk this trade uses (`account.risk_usd` from `fetch_analysis_data.py`, computed as current equity × the user's own `/setrisk` percentage — never a value asked of the user inline, and never invented if `equity_usd` is unset), the resulting **portfolio heat** if this trade is taken (total $ at risk across every open position, including Core, divided by equity) against its cap, and the current **Core/Swing and SPY/QQQ-within-Core allocation** against its target. **Unlike rule 18's regime gate, none of this ever blocks the decision line or changes the grade** — this is disclosure, not a gate, per explicit user direction: the system's job is to make sure the real number is always visible, the user decides what to do with it. State plainly when a figure can't be computed yet (`equity_usd` unset) rather than guessing — same "missing input" posture as anything else this system won't invent.
    - **Deterministic backstop, not a second judgment call:** `bot/report_lint.py` checks only that a report whose own `portfolio_heat_after` exceeds the stored cap actually contains the disclosure warning — it never judges the heat number itself or touches the decision line, since nothing here gates the decision to begin with. Contrast with rule 18's backstop, which does check a decision-line contradiction, because rule 18 is the one rule in this list that actually blocks.

20. **Sector/correlation-group concentration disclosure — same disclosure-only treatment as rule 19, never a gate.** Every `/screener` report must state the ticker's own correlation group (`account.sector_group` from `fetch_analysis_data.py`, defined in `bot/sector_map.py` — say "sector unclassified" plainly rather than guessing one for an unmapped ticker) and what % of the swing (non-Core) book that group would hold including this trade (`sector_pct_after`), against its cap (`account.sector_cap_pct`). Found in the strategy review: ~84% of the real book turned out to be one correlated bet (SPY+QQQ+NVDA+AMZN, since NVDA/AMZN are themselves top QQQ holdings) with nothing anywhere surfacing it. **This never blocks the decision line** — same explicit user direction as rule 19: the system discloses, the user decides.
    - **Deterministic backstop, not a second judgment call:** `bot/report_lint.py` checks only that a report whose own `sector_pct_after` exceeds `sector_cap_pct` actually contains the disclosure (`sector_disclosed=true`) — it never judges the sector classification itself or touches the decision line, identical shape to rule 19's own backstop.

21. **Cash-usage disclosure — same disclosure-only treatment as rules 19/20, never a gate.** `risk_usd` (rule 19) bounds RISK, not DOLLARS — a tight-stop trade can cost far more in actual cash than a wide-stop trade for the identical risk figure, since risk is only the slice between entry and stop while the full share price is what's actually paid. Every `/screener` report must compute this trade's own `cash_required_usd` (qty × entry) against `account.cash_available_usd`, and disclose plainly when it exceeds `account.cash_usage_warn_pct` of available cash — **stating the actual share count (qty) the full position needs, not only the dollar/percentage figures**; a percentage alone isn't actionable, the reader needs to see the real number of shares this specific warning is about without having to cross-reference the sizing table separately. Found real, 2026-07-19: closing a modest risk-dollar gap on an existing tight-stop position would have required roughly 17-20x that gap in actual cash — more than the account's entire remaining cash — with nothing anywhere surfacing that a single trade could quietly consume most of the money on hand even while portfolio heat stayed well under its own cap. **This never blocks the decision line or reduces the computed size** — same explicit user direction as rules 19/20: the system discloses, the user decides.

22. **Breakout-day volume confirmation — DISCLOSURE ONLY as of 2026-08-03; the ×0.5 sizing derate is removed.** The 15-year / 43,957-break backtest measured this directly and it pointed the wrong way: breaks on **below**-average volume averaged **+0.13R** against **+0.08R** for above-average volume (t=3.6, a real difference, not noise). 23. **Market regime is a numeric formula, not a free-form judgment call — `bot/regime_formula.py` is the single source of truth.** Found in the strategy review: rule 18's regime gate is the single highest-leverage decision in this entire system (it alone decides whether ANY buy order is allowed), yet had zero objective backstop — a fresh, unaccountable AI read of the SPY/QQQ chart every single run, with no way to check consistency or backtest whether the calls were ever right. `regime_formula.classify_regime()` replaces that judgment call with a mechanical score computed from SPY+QQQ's moving-average stack (price vs. SMA20/50/150, ±3 per index), trend structure (ascending/descending recent swing highs/lows, ±2 per index, using the same mechanical pivot detection already used elsewhere — never a re-derivation of which pivot "matters"), and whether the two indexes agree (±1) — summed into one score, mapped onto the same six regime labels this system already uses. `structure_break` additionally requires a real, confirmed close below the lookback low (~6 trading months) — a deep-but-still-above-support pullback is `risk_off`, not an overstated break it didn't actually earn. **Honest caveat, stated plainly, not hidden:** the score-range cutoffs are a reasonable first draft, not derived from backtested data — same posture as rule 4's 0.7x ATR noise floor, worth checking against real history once there's a track record, not something to trust blindly forever.
    - **`fetch_analysis_data.py`/`fetch_monitor_data.py` compute this once per run and report it as `market_regime_formula`** — every `/screener`, `/monitor`, `/monitorall`, and `/playbook` call copies this value verbatim into the decision JSON's `market_regime` (screener, playbook) or `regime_now` (monitor) field. **Never re-derive, re-classify, or second-guess the formula from the chart.** (Extended to `/playbook`/STRATEGY_v3.md 2026-07-20 — its §ב "מצב סיכון" call had been the one remaining fresh eyeballed read in an otherwise system-wide rule; now sourced from the formula the same way, and surfaced as its own line in the Telegram summary.)
    - **The only permitted deviation is a disclosed, written-down override — never a silent substitution.** If there's a genuinely real, specific reason the formula's call doesn't fit right now (a scheduled Fed/CPI/NFP release today, major breaking news) — state that reason explicitly in `regime_override_reason` and use the overridden value in `market_regime`/`regime_now`, while `market_regime_formula` still holds the formula's original, untouched call so the deviation stays visible. **Never override just because the call looks surprising** — surprising is not the same as wrong, and the whole point of this rule is that the call is no longer free-form. This system does not (yet) restrict override authority to the user alone by any mechanical means — that's a real, known limitation, not a design choice; the actual enforcement today is that every deviation must be visible and explained, never silent, which is the property that mattered most.
    - **Deterministic backstop, not a second judgment call:** `bot/report_lint.py` checks only that `market_regime`/`regime_now` matches `market_regime_formula` unless `regime_override_reason` is present and non-empty — it never judges whether the override reason is any good, only that a real deviation always comes with a stated one, never nothing.
    - **`x_posts` context (2026-07-22, `bot/fetch_x_feed.py`'s `recent_related_posts`/`recent_macro_posts` fields) may inform a disclosed `regime_override_reason` or a `/monitor` note, exactly like the existing "breaking news" allowance above — real fetched tweet text instead of the model's own assumed knowledge of what's happening.** It is informational context only, at the same standing as any other input to that written-down reason. **It may never justify skipping, widening, or delaying a stop-loss, and never bypasses an entry/exit rule directly** — this system is deliberately hardened against discretionary overrides of its mechanical rules, and a live social-media feed is exactly the kind of input that could otherwise invite more discretion, not less.

24. **Stop buffer — the stop sits a small distance below the structural low itself, never exactly at it.** Every stop-placement rule in this file and in `SCREENER_v3.md`/`STRATEGY_v3.md` that says "below [level]" — the breakout base, the retest low, the relevant Higher Low, the Reclaim candle's low, the Flush low, the gap candle's low, or the highest-qualifying daily low chosen by the post-tranche trailing-stop method — means **`stop = level − 0.15x ATR14`**, not the raw level price itself. A stop set exactly at the low gets filled by any wick that merely touches the level, even when the level itself holds and no real breakdown occurs; the buffer absorbs that ordinary intrabar noise without loosening the stop enough to matter. **This is a separate, smaller check from rule 4's ≥0.7x ATR14 noise floor, not a restatement of it:** rule 4 tests the distance between the *reference price* and the stop (is the whole stop placement too tight to be signal at all); this rule tests the small gap between the *stop* and the *structural level backing it* (is the stop sitting exactly on top of the level it's supposed to sit below). Both checks apply together — passing one never substitutes for the other. State the buffer explicitly wherever a stop is cited, e.g. *"stop 940.80 = base low 945.00 − 0.15×ATR14 (28.00 × 0.15 = 4.20)"* — a stop shown as a bare level price with no buffer arithmetic is under-specified, same standard as rule 14's "below the daily low is not a complete instruction on its own." (Found via user review, 2026-07-20: stops were consistently being placed at the literal candle low with no cushion beneath it.)
    - **Deterministic backstop, added 2026-07-30 full-system checkup:** this rule had no code check at all until now. `primary_setup`/`alternate_setup` (SCREENER_v3.md, `deliver_report.py`) and each open position (STRATEGY_v3.md, `deliver_playbook_report.py`) must now carry `stop_basis_level` — the raw structural price identified BEFORE the buffer is subtracted, copied verbatim, never invented. `report_lint._lint_stop_buffer` checks `stop <= stop_basis_level − 0.15×ATR14`; a stop sitting closer to the level than that (including exactly at it) is flagged as a real finding, same severity family as rule 4's noise-floor check.

25. **Past-lesson context (`/reflect`) is NOT fed into a new thesis — switched off 2026-08-10, owner's decision. Reflections are still written and still stored; nothing reads them at decision time.** The reasoning, in the owner's own words: *"it can make me take decisions based on history, and we want it to be clear for future understanding of the data collection in order to be able to be accurate — this rule basically summarises the results before we have the data."*

    - **It contaminates the only measurement that can settle anything.** The shadow book exists to answer whether THESE RULES pick winners. If a past lesson moves a decision, every recorded outcome is rules plus recall, and the two can never be separated afterwards. Collecting clean data now is worth more than a hint today.
    - **This is exactly what separates rule 25 from rule 26**, which looks like the same kind of disclosure and is not: rule 26 rests on 305 backtested trades across 80 tickers and 26 months. That is evidence. Rule 25 rested on one trade. Rule 26 stays on; rule 25 goes off.
    - **What is NOT switched off:** `/reflect` itself, `closing_summaries`, `thesis_validated`, or the lesson text. Those are data and stay exactly as they are — they are a labelled record of what actually happened, and the shadow-book analysis in a few months is the right place to read them, all at once, with a sample big enough to mean something. What stopped is reading them ONE AT A TIME, at the moment a decision is being made.
    - **The one thing genuinely lost, stated plainly:** some reflections are about MECHANICS rather than judgment ("the exit was unmatched — it did not fill at either planned level"). Those are bugs, not trading opinions, and they deserve to be fixed in code rather than remembered at decision time. If a reflection describes something broken, raise it as a defect; do not rely on this rule to resurface it.

    The original rule follows, for the record: **Past-lesson context (`/reflect`) is informational only, never a gate — same disclosure-only family as rules 19–22.** Before finalizing a new `SCREENER_v3`/`MONITOR_v2` thesis, check `persistence.get_ticker_lessons(ticker)` (past reflections on this exact ticker) and `persistence.get_recent_cross_lessons(exclude_ticker=ticker, setup_type=<setup being considered>)` (recent reflections on the same setup family elsewhere). If either returns a lesson worth noting, name it explicitly in the analysis (e.g. *"last Reclaim on this ticker stopped out on noise — see 2026-07-20 reflection"*). **This never blocks, downgrades, or resizes the current setup by itself** — a past lesson is context for the human reader, not a mechanical veto; the current chart's own rules (1–24) are what actually gate the decision, exactly like rules 19–22's own disclosures never touch the decision line. Only rows with `thesis_validated IS NOT NULL` are ever surfaced (a still-pending, un-reflected close has no lesson yet to inject) — see `MASTER_SYSTEM_SPEC.md` §9's `/reflect` entry for how those rows get written in the first place.
    - **Deliberately no deterministic backstop:** unlike rules 19–22, whether a genuinely relevant lesson existed and got mentioned is a judgment call about relevance, not a checkable number — `bot/report_lint.py` has nothing mechanical to verify here, same posture as rule 2's stop-base test or rule 12's Fibonacci-anchor test.

28. **Position size has a hard floor and a hard ceiling — the shrink multipliers may halve a trade, never quarter it, and nothing may exceed one full risk unit. `bot/size_policy.py` is the single source of truth.** Found in the 2026-08-02 trade review, read straight off the real `positions` table rather than derived from theory: risk actually taken per trade ranged from **0.08% to 2.26%** of equity against a stated 1% rule, with the *typical* trade at 0.2%–0.4%. Both ends were broken, each for its own reason, and nothing anywhere in the code looked at the final number.
    - **The floor exists because SCREENER_v3.md section ד stacks three independent shrink multipliers with nothing bounding their product:** the volatility multiplier (low=1.0 / medium=0.75 / high=0.5), rule 18's `neutral_choppy` ×0.5, and rule 22's weak-breakout-volume ×0.5. All three together is **×0.125**. Worse, `regime_formula.py` has read `neutral_choppy` every single trading day since 2026-07-20, so the middle multiplier is not an occasional derate — it is effectively permanent, and the ceiling on every trade has quietly been half size or less for weeks. Real consequence: XLF, the best trade in the entire book at **+1.79R**, was sized at 0.20% risk, so it banked roughly a fifth of what a full-size position would have made. A correct call sized at a quarter is a quarter of a correct call — the analysis being right does not help if the position is too small to matter. **The floor is ×0.5 on the product of all multipliers**, on the reasoning that a single documented derate is itself exactly ×0.5, so one derate's worth of caution is the most that any stack of them may express.
    - **The ceiling exists because the single largest loss in the book was a sizing error, not an analysis error:** CRDO was entered at 2.26% risk — 2.3× the rule — on this system's own F-graded idea, and lost **48% of every dollar lost across all closed trades**. Ten other losing trades together did about the same damage as that one. **The ceiling is 1.0× the account's full risk figure** (`effective equity × risk_pct`), after every multiplier and after whole-share rounding.
    - **Deliberately asymmetric, and worth saying out loud: there is no upsize path.** Every multiplier in this system is ≤1.0, and rule 28 keeps it that way — an A-grade setup in a supportive regime gets the same ceiling as a C-grade one. That is a real limitation, not an oversight; adding a conviction-based upsize is a genuine strategy change that needs its own decision, not a side effect of adding a floor.
    - **A trade that cannot fit inside the band is refused, never quietly oversized.** When a single share already risks more than one full position allows (a very expensive stock with a wide stop), `size_position()` returns qty 0 with a stated reason. An honest "this cannot be sized within the rules" is the correct output; rounding up to one share and calling it a starter is not.
    - **Every `/screener` report that proposes an order must carry a `sizing` block** (`entry`, `stop`, `qty`, `risk_usd_target`, and `multipliers` as one entry per column already shown in section ד's table) — the same verbatim-copy convention as `atr_at_build` and `stop_basis_level`, never re-derived at delivery time. Omitted entirely for Watchlist/No Trade, which have no order to size.
    - **Full size is the default, not the ceiling (added 2026-08-09).** Once every multiplier was removed on 2026-08-03, the 0.5×–1.0× band stopped describing a range to choose within: with no derates left, the only correct answer is one full risk unit. The band survives as the hard legal boundary, but anything landing below **0.9×** now requires a written reason in `sizing.size_reduction_reason` — `cash_limited` being the real and common one (the trigger fired on a day the account did not hold enough free cash for the full quantity; two live fills on 2026-08-03 and 2026-08-06 were exactly this, at 0.13% and 0.18% risk, and nothing recorded why). A stated reason makes a small position a decision; an unstated one makes it a bug that looks like a decision. **The reason is recorded, never judged** — same disclosure-only posture as rules 19–21.
    - **Deterministic backstop, and unlike rules 19–22 this one is a real arithmetic check, not a disclosure check:** `report_lint._lint_size_floor()` flags the final risk landing outside the 0.5×–1.0× band (`size_outside_bounds`), and — separately — landing under 0.9× with no `size_reduction_reason` given (`size_below_full_no_reason`). It never re-picks the trigger or the stop — Category B is untouched; it only checks the quantity those choices produced. Consistent with every other lint finding, it warns loudly and never blocks the send. The old `size_multiplier_below_floor` check retired with the multipliers themselves.
    - **User-facing, and the reason this rule was asked for in the first place:** the Telegram size block used to show quantity, total cost, portfolio heat and cash used — and none of those answer *"is this a full position or a small one?"*. `deliver_report.py` now appends a deterministically computed block (`size_policy.format_size_lines_he()`) stating the trade's real dollar risk, its percentage of the account, and its size in plain words ("פוזיציה מלאה" / "חצי פוזיציה" / …) next to what a full position would have been. Computed in Python and appended, never left to the model's own template — same reasoning as `deliver_position_status_report.py`'s stop-distance line.

29. **The four decision words are defined, and the decision line may never claim more than the facts permit — `bot/decision_policy.py` is the single source of truth.** `SCREENER_v3.md` has listed four possible decision lines since the beginning — Buy Now / Buy Only If Confirmed / Watchlist / No Trade — and never once defined them, so the choice was made fresh, by judgment, on every run. The 2026-08-02 full rescan made the drift visible in a single table: MSFT, RKLB and SPOT all came back **No Trade** with zero qualifying targets, and **ONDS came back Watchlist with zero qualifying targets** — identical facts, two different words. (PLTR, the fifth D-grade that day, correctly read Watchlist because it genuinely *had* a target paying 2.11:1.) The user spotted this unprompted before any check did: *"i have stocks with the same grade but different call."*
    - **The dividing line is the target, not the grade** — this is the part that was being got wrong. A grade says how good a trade is; the decision line says whether an order can be placed at all, and those are different questions:
      - **No Trade** — nowhere to sell. No level clears rule 3's gate in either setup, so there is no trade to place, not merely one to wait for.
      - **Watchlist** — a real target exists, but something is wrong *today*: the chart is still falling, earnings land inside the holding window, price is too extended, the live grade is D (rule 27), or the regime blocks orders (rule 18).
      - **Buy Only If Confirmed** — a real target exists, grade C or better, nothing wrong. The only missing thing is the price. An order can be written now and left to wait.
      - **Buy Now** — all of the above, and the trigger has already confirmed on a real settled daily close.
    - **The two buy words are deliberately NOT ranked against each other.** Which one is right turns on whether the trigger already fired, and `decision_policy.max_allowed_decision()` is never given that fact — so it permits either. A first version returned `Buy Only If Confirmed` as the ceiling and thereby flagged every legitimate screener `Buy Now`; that false alarm was caught by the existing clean-decision test, and it is exactly the kind of noise that trains a reader to ignore real findings.
    - **A D grade is never automatically No Trade.** D means *never an order*, not *throw it away* — a D can become a B next week when the regime shifts or an earnings date passes, and the nightly refresh is what would catch that. Deleting every D would quietly bin ideas that are about to get good.
    - **Cold list — a No Trade leaves the active list without being forgotten.** "Nowhere to sell" is almost always a statement about where price is standing right now, not about the company: rule 7 already documents two real cases where the *identical chart* produced a qualifying target purely from a different entry price (ANET's 179.80 level failed from a 179.80 entry and passed at 2.54:1 from ~162; MU's identical target went from 1.78:1 to 8.19:1). So a No Trade thesis moves to `status='cold'` (`persistence.set_cold`) — off the list the user reads, but re-screened automatically every **3 trading days**, up to **3 attempts** (`COLD_RECHECK_TRADING_DAYS` / `COLD_MAX_RECHECKS`), by `refresh_pending.py`. Leaving it `pending` clutters the one list that has to stay short enough to read; deleting it is worse, because `refresh_pending.py` only rebuilds pending rows, so a dropped idea is never looked at by anything again. After the third failed attempt it is **reported with a ready-to-send `/drop` line and left alone — never auto-deleted**, same posture as every other destructive action in this system.
    - **The shelf also catches a thesis whose price fell under its own stop** (added 2026-08-11, the user's call). Such an idea is never rebuilt — rebuilding a broken chart spends a full ~25 minute screener run manufacturing a fresh reason to look at a falling stock, in the hours meant for ideas that can still be bought — but it also cannot sit on the waiting list forever printing the identical `/drop` line every night, which is how that whole section stopped being read and how a *newly* dead idea came to hide among the old ones. So: night one, the full line with its ready `/drop`; nights after, a one-line count (`🔴 3 עדיין נראים גמורים: …`); after **5 consecutive nights** with no answer (`persistence.DEAD_NIGHTS_BEFORE_COLD`), `persistence.set_cold` moves it to the same shelf, reported and named. Nothing is deleted, nothing is re-screened that night, and the cold re-check looks at it again in 3 trading days — queued **last**, behind every live idea. The streak resets the moment price is back above the stop, and on any fresh build (that build has a new stop, so a streak measured against the old one says nothing about it). The re-check clock runs from `cold_since`, the day it was shelved, not `date_built` — an idea built in May and shelved tonight would otherwise be "due" immediately, which is the burnt hour this rule exists to avoid.
    - **Plain-words reasons, from a fixed vocabulary.** `rejection_reasons` is free text, and the same situation really did come back as `trigger_not_fired`, `trigger_not_confirmed`, `no_live_trigger`, `trigger_pending` and `awaiting_trigger_confirmation` across one week — fine for a human reading one report, useless for showing a consistent "why not yet" line and useless for counting anything later. `decision_policy.explain_reasons()` maps the stored tokens onto a fixed short list of everyday sentences (substring-matched, so existing tokens keep working), capped at two per idea and ordered so the reason that actually decided the outcome wins over "the price hasn't got there yet", which is true of every waiting idea and says nothing. Shown on every `/pending` card.
    - **The decision is shown as a sign in every list that mentions the ticker** (added 2026-08-03 on the user's request). `/list`, `/pending`, `/monitor` and `/monitorall` all showed the levels, the status tier and the grade, and none of them said which of the four decisions the thesis was actually sitting on — a ticker being watched and a ticker with an order written and waiting for its price looked identical everywhere. `decision_policy.decision_sign()` (emoji only, for the one-line `/list`) and `decision_policy.decision_line()` (emoji + `מה נקבע בתזה:` + plain Hebrew) render it: 🟩 Buy Now · 🔷 Buy Only If Confirmed · 👁 Watchlist · 🚫 No Trade · ❔ nothing stored. Three things are deliberate. The emoji **do not overlap MONITOR_v2.md's ⚪/🟡/🟢/🔴 status tiers** — a "watchlist" sign that looks like a "still far from the trigger" sign is worse than no sign. Buy Now is the one place the two vocabularies want the same color (green means "go" in both), so it is separated by **shape**: 🟩 square for the decision, 🟢 circle for the status tier — every status tier is a circle, no decision sign is. The value is read **from the stored `thesis.decision` column, never from the check's own JSON** — re-asking the model for a decision that is already written down is how the two drift apart, which is the whole failure this rule exists to stop. And the line **names its own source**, so a live 🟢 under a stored 👁 reads as two facts (what the price did today, what the thesis decided at build) rather than a contradiction.
    - **Deterministic backstop:** `report_lint._lint_decision_word` recomputes the ceiling from the report's own fields (does either setup have a `targets[]` entry, what grade, what regime) and flags a decision line that claims more. It never decides which level is a target — same consistency-check-only shape as rules 18/23/27's own backstops.

30. **A realized tranche is spent — a target that has been sold at can never be sold at again, and the system must say out loud which piece is next. `indicators_core.build_tranche_plan()` is the single source of truth.** Found via a real miss the user caught, not a check: **ASTS** (position 25, entry 58.86, 211 shares) had exactly one qualifying target on file, 72.36, split 40% there / 60% Runner under rule 7. It was sold at on 2026-08-05 (84 shares) and sold at **again** on 2026-08-06 (45 shares) — and both rows landed in the journal as `exit_reason='target_1'`, because `derive_exit_reason()` matched purely on price and had no memory of the first fill. Rule 7 has always written the allocation down; nothing anywhere had ever written down that a piece of it was **done**. Three consequences, all invisible until asked about:
    - **The Runner is what gets eaten.** Rule 7 gives each numbered target a fixed percentage and defines the Runner as whatever is left over, so a target that appears to fill twice silently doubles its own allocation out of the Runner — the 5-year backtest (the retired `bot/backtest_lab.py`, 326 trades; backtest notes kept privately) found the Runner tranche *is* the entire edge (**+40.6R with it, −33.3R without**). ASTS's Runner went from a planned 127 shares to a real 82 with nothing flagging it.
    - **Every report kept presenting a spent level as pending.** `/positions`' approaching-target status line, `/playbook`'s target table and `/open` all read the stored targets straight and had no field telling them otherwise, so the same "you're close to your target" heads-up (rule 3) fired again on a level there was nothing left to sell at.
    - **The stop was never the problem.** ASTS's stop had already trailed correctly from 51.84 to 54.78 (the 2026-08-03 low 55.74 − 0.15×ATR, rule 24); the higher lows built 08-04→08-06 all sit inside rule 4's 0.7×ATR noise floor, so no further raise was permitted. The tranche accounting was the only thing broken.
    - **What is enforced now.** `derive_exit_reason()` takes the set of targets a prior exit on the same position already realized and skips them; a later sell above the stop with no unrealized target left is recorded as **`runner_trim`**, its own honest reason, distinct from a discretionary `unmatched`. `build_tranche_plan()` returns every tranche with `planned_qty`/`filled_qty`/`status` plus `next_label`/`next_price`/`runner_qty_left`, computed in code from the position's own stored targets and its real `exits` rows — attached by `persistence` to **every** open position it hands out, so `/open`, `/exit`'s confirmation, `/positions` and `/playbook`'s fetch payload all read the same numbers and none of them can re-derive the split by judgment. When `next_label` is `runner` there is no price to name: those shares leave on the trailing stop only. Any drift between the written plan and the real exits (a tranche sold past its planned size, shares exited with no Runner to draw them from) comes back in `warnings` and is surfaced verbatim rather than absorbed.
